# 秋招求职复盘 Agent 设计

日期：2026-08-03

## 1. 目标

构建一个面向中国校招场景的 AI 求职复盘系统。用户在 Codex 对话中用自然语言记录投递、流程变化和面试经历，系统通过 MCP 服务将信息可靠地写入私人 Notion，并使用 DeepSeek 整理面经、提取薄弱项、生成复习任务和周期复盘。

项目代码公开，真实求职数据私有。公开 GitHub 仓库只包含代码、数据结构、提示词、脱敏评测样例和项目文档，不包含真实公司记录、面经、联系人、Notion 页面地址或密钥。

## 2. 产品原则

- 对话是主要录入入口，Notion 是日常查看和维护入口。
- Notion 是真实数据的唯一事实来源，GitHub 不是隐私数据备份介质。
- 原始记录优先于 AI 产物；模型分析不能覆盖用户原文。
- 信息不足时允许先保存并标记待补充，不通过虚构填满字段。
- 第一版尽快投入真实使用，再根据真实记录逐步扩展为作品级项目。
- Agent 能力集中在工具调用、结构化抽取、复盘和评测，不以普通 CRUD 前端为重点。

## 3. 系统边界与架构

```text
Codex 对话
  |  识别记录投递、更新进度、整理面经、生成复盘等意图
  v
Job Hunt MCP Server（Python）
  |- 投递管理工具
  |- 面试与面经工具
  |- 周报与统计工具
  |- 数据校验、消歧和去重
  |- 隐私检查
  `- DeepSeek 模型适配器
  v
Notion 私有空间
  |- 投递 Applications
  |- 动态 Activity Log
  |- 面试 Interviews
  `- 改进项 Review Tasks
```

### 3.1 组件职责

- **Codex**：第一阶段理解自然语言、选择 MCP 工具并组织参数。
- **MCP Server**：负责校验、幂等写入、状态流转、查询、统计和错误恢复。业务正确性不依赖对话记忆。
- **DeepSeek**：第一阶段用于面经结构化分析，后续逐步承担字段抽取、复盘和计划生成。模型接口按 OpenAI-compatible 形式封装，避免业务层绑定单一供应商。
- **Notion**：保存全部真实求职数据并提供私人看板。
- **GitHub**：公开项目代码、Schema、脱敏样例、评测框架、CI 和部署文档。
- **本地状态**：只保存页面标识、同步状态及脱敏评测数据，不长期复制完整隐私数据。

### 3.2 技术选择

第一版采用 Python 3.12、FastMCP、Pydantic、Notion API、DeepSeek OpenAI-compatible API 和 pytest。第一版不开发独立前端；后续网页或飞书入口复用相同 MCP 和业务服务。

## 4. Notion 数据模型

### 4.1 Applications

每个秋招批次中的公司岗位对应一条当前记录。

核心字段：

- 公司
- 岗位
- 秋招批次
- 方向
- 地点
- 投递渠道
- JD 链接
- 简历版本
- 投递日期
- 当前阶段
- 优先级
- 截止日期
- 下一步
- 最终结果
- 结束原因
- 是否待补充
- 归档状态

第一版将公司保留为文本字段；实际出现同一公司多岗位管理需求后，再评估拆分公司数据库。
秋招批次不根据日期静默推断，而是在首次设置时由用户指定默认值；单条投递仍可覆盖该默认值。

### 4.2 Activity Log

保存投递创建、状态变化、约面和结果等不可变事件，用于每日记录、阶段耗时和转化漏斗统计。

核心字段：

- 事件时间
- 关联投递
- 操作唯一 ID
- 事件类型
- 原状态
- 新状态
- 备注
- 同步状态

### 4.3 Interviews

每轮面试对应一条记录，一次投递可关联多轮面试。

核心字段：

- 关联投递
- 面试轮次
- 时间
- 形式
- 结果
- 原始笔记
- 结构化面经
- 自评分
- 总体复盘
- 模型版本
- Prompt 版本
- 分析状态

### 4.4 Review Tasks

保存面试暴露的知识点、能力短板和可执行改进任务。

核心字段：

- 分类
- 知识点或问题
- 来源面试
- 掌握程度
- 出现次数
- 复习行动
- 截止日期
- 完成状态
- 确认状态

新生成的改进项默认为待确认。相同知识点再次出现时更新次数和关联来源，而不是重复创建任务。

### 4.5 状态模型

默认投递状态为：

```text
待投递 -> 已投递 -> 笔试 -> 面试 -> 意向 -> Offer
```

面试轮次记录在 Interviews 中，不将一面、二面等全部编码进投递状态。非线性变化允许通过 Activity Log 保留，例如从面试退回笔试补测。流程是否结束与当前阶段分离，最终结果使用“进行中、Offer、被拒、主动终止、无回应”记录，并可补充结束原因。

## 5. MCP 工具接口

第一版只暴露少量高内聚工具：

| 工具 | 职责 |
| --- | --- |
| `record_application` | 新增投递；检测相同公司、岗位和批次的已有记录 |
| `update_application_stage` | 更新当前阶段并追加 Activity Log |
| `record_interview` | 保存面试轮次和原始面经 |
| `analyze_interview` | 使用 DeepSeek 生成结构化面经和候选改进项 |
| `list_follow_ups` | 查询临近面试、截止日期和待复习事项 |
| `generate_review` | 生成日复盘或周复盘、转化漏斗和准备建议 |

### 5.1 交互约束

- 写入后返回简短回执，明确新增或修改的内容以及待补充字段。
- 非关键字段缺失时先保存，不反复阻断用户。
- 使用“公司 + 岗位 + 秋招批次”匹配投递，并以操作唯一 ID 保证重试幂等。
- 模糊匹配到多个投递时必须让用户消歧。
- 删除采用归档语义，并要求用户明确确认。
- DeepSeek 输出必须先通过 Pydantic Schema 校验，不能直接自由写入 Notion。

## 6. 面经分析工作流

结构化面经包含：

- 面试流程与时长
- 技术问题
- 项目追问
- 行为问题和反问
- 用户回答摘要（仅在原始记录包含回答时生成）
- 表现判断及其原文依据
- 更好的回答思路
- 暴露的薄弱点
- 可执行复习任务

分析必须区分用户明确陈述与模型推断。推断字段带置信度；没有记录回答时不得虚构回答或表现。原始面经永久保留，可以用新版模型或 Prompt 重新分析。

复习建议必须可执行，例如“复习 Hybrid Search 并完成一个最小对照实验”，不能只给出“加强 RAG”等泛化表述。

## 7. 复盘与统计

日复盘至少包含：

- 当日新增投递及状态变化
- 次日临近事项
- 新增面试薄弱项

周复盘至少包含：

- 投递数量和渠道分布
- 各阶段转化率
- 各阶段平均停留时间
- 面试问题领域分布和重复出现的知识点
- 未完成的高优先级复习任务
- 下一周可执行计划

复盘由现有数据库实时生成 Notion 页面，不创建重复的汇总数据库。

## 8. 可靠性与错误处理

Notion 不支持跨页面事务。状态更新采用可恢复流程：

1. 创建同步状态为“待处理”的 Activity Log 事件。
2. 更新 Application 的当前状态。
3. 将 Activity Log 事件标记为“已完成”。

失败后通过 Notion 中的待处理事件恢复，不需要在本地长期保存敏感操作载荷。每次操作包含唯一 ID，重试不会重复生成记录。

Notion 限流、网络超时和 DeepSeek 不可用时，MCP 返回明确的部分完成状态。面试原文可先保存，模型分析进入待处理状态并在后续重试。任何失败都不能以静默丢失记录结束。

## 9. 隐私与安全

- Notion Token 和 DeepSeek API Key 仅通过环境变量提供。
- 日志默认不保存完整面经、JD、联系人信息或自然语言原文。
- 日志使用内部记录 ID、操作 ID、结果状态和错误类别完成诊断。
- 公开演示数据全部人工构造，不从真实数据自动脱敏生成。
- 提交与 CI 检查密钥、Notion URL、真实记录和个人信息泄漏。
- 真实求职数据不自动提交到公开 GitHub。
- 数据备份采用可选的本地加密导出，与公开项目仓库隔离。

## 10. 评测与测试

### 10.1 脱敏 Agent 评测集

评测覆盖：

- 新增投递与更新状态的意图识别
- 公司、岗位、日期、轮次等字段抽取
- 相似投递的去重与消歧
- 面试问题分类和知识点归并
- 缺失信息下的非虚构行为
- MCP 工具选择和参数正确率
- Schema 合法率
- 改进任务的可执行性
- 隐私泄漏检查

每次更换模型或 Prompt 后运行回归评测，报告成功率、字段准确率、幻觉案例、延迟和调用成本。公开评测样例均为合成数据。

### 10.2 工程测试

- 单元测试：Schema、日期解析、状态规则、去重、幂等和隐私过滤。
- MCP 合约测试：工具名称、输入输出结构和错误语义。
- 模拟集成测试：使用 Notion 和 DeepSeek 的测试替身验证工作流。
- 可选真实集成测试：仅针对用户授权的测试数据库运行，不接触正式数据。
- 端到端评测：从自然语言输入到预期工具调用和结构化结果。

## 11. 分阶段交付

### 阶段一：1 至 2 天可用版本

- 创建 Notion 数据库和字段
- 建立 Python MCP 服务
- 完成投递新增、状态更新和面经保存
- 完成 DeepSeek 基础面经整理
- 建立核心 Schema、幂等机制和基础测试

### 阶段二：约 1 周增强版本

- 改进项归并和待办提醒
- 日复盘与周复盘
- Notion 写入恢复机制
- 核心脱敏评测集和回归报告
- 隐私扫描和 CI

### 阶段三：2 至 3 周作品级版本

- 独立 DeepSeek Agent 工作流
- 完整评测、成本与延迟报告
- 部署方式和演示环境
- 合成演示数据、架构文档和项目展示材料
- 为网页聊天或飞书入口提供稳定后端接口

## 12. 完成标准

- 一句话可以新增投递，重复执行不会生成重复数据。
- 状态变化保留完整历史，并可在部分失败后恢复。
- 面经原文与 AI 分析结果同时存在。
- 信息不足时不编造回答、表现或面试结果。
- 能生成可信的日复盘、周复盘和复习清单。
- 公开仓库不包含密钥、Notion 私有地址或真实求职数据。
- 单元测试、MCP 合约测试、模拟集成测试和脱敏 Agent 评测通过。

## 13. 已确认决策

- 采用“对话录入 + Notion 私有数据 + GitHub 公开代码”的混合方式。
- 目标岗位为 AI Agent / LLM 应用工程师。
- 第一入口为 Codex MCP，后续扩展网页或机器人。
- 采用分阶段交付，优先让第一版尽快用于真实秋招。
- 使用 DeepSeek，并通过兼容接口隔离模型供应商。
- GitHub 代码公开，真实求职数据始终私有。
