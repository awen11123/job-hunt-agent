# Notion 面经统一模板设计

## 目标

将现有两条面经统一为相同的正文结构，并把该结构作为后续所有面经的默认模板。Notion 仅保留面经与面试答案题库；投递进度继续由私有 WPS 工作簿维护。

## 隐私边界

- 仓库只保存通用模板、迁移逻辑和无真实数据的测试。
- 公司名称、岗位、面试正文、Notion 页面 ID、数据库 ID 和访问令牌不得写入 Git。
- 真实内容只通过运行时 Notion API 读取和写入。

## 标准正文结构

每条面经按以下顺序使用七个二级标题：

1. 基本信息
2. 面试主线与整体评价
3. 核心问题复盘
4. 项目与回答亮点
5. 主要短板
6. 改进与准备建议
7. 后续动作

具体技术模块使用三级标题。面试问题使用编号列表；亮点、短板和建议使用项目列表；代码继续使用代码区块；待办继续使用待办区块。

## 现有内容迁移

### 已有结构化面经

- 从数据库属性生成“基本信息”。
- 将总体判断、岗位匹配和面试官考察主线归入“面试主线与整体评价”。
- 保留全部核心问题、回答、考察点和改进建议，将技术模块降为三级标题。
- 将项目背景和有效回答归入“项目与回答亮点”。
- 将风险诊断、准备建议和待确认事项分别归入后三章。

### 独立子页面面经

- 读取独立页面的全部顶层区块。
- 保留段落、列表、引用、分隔线、代码和待办的文本及语义类型。
- 将正文重排后写入对应的面试数据库记录。
- 只有在新区块、章节、代码块和行动项核验通过后，才把旧独立页面归档到 Notion 回收站。

## 后续新增面经

- 新面经直接创建为面试数据库页面，不再创建独立子页面。
- 页面创建时一次性写入七章骨架，再填充用户提供的面试内容。
- 缺失的信息写成明确的“待补充”，不得虚构现场回答、日期、公司或面试结果。
- 原始记录与整理后的判断必须区分，改进建议不得冒充候选人的现场回答。

## 安全与恢复

- 迁移采用“先追加、后核验、再归档旧内容”的顺序。
- 任一写入或核验失败时停止归档，旧内容继续作为可恢复来源。
- Notion 删除统一采用归档，保留回收站恢复能力。
- 重复执行前检查标准章节是否已经存在，防止重复追加。

## 验收标准

- 面试数据库仍有两条现有记录。
- 两条面经都恰好包含七个标准二级章节，顺序一致。
- 已有的核心问题数量不减少。
- SQL 等代码区块完整保留。
- 技术行动项和后续事项完整保留。
- 旧独立面经页面仅在迁移验证成功后归档。
- 面试答案题库页面保持原有区块数量和内容。
- 仓库不包含真实求职数据、Notion 标识符或访问令牌。
